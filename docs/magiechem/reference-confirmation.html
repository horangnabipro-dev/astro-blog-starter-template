Part 1 — Design Reference Confirmation
§06

How the three references divide the work

They are not three flavours to blend. Each one owns a different layer of the product, and where they disagree, the order below decides.

Apple — interaction, craft, hierarchy MAPEI — content architecture, vocabulary Fiverr — browsing composition
Apple governs
How it behaves and how it feels. Every navigation, motion, spacing and typographic decision defaults to Apple.
MAPEI governs
What the content is called and how it is organised. Taxonomy, terminology, document rigour.
Fiverr contributes
Four specific composition patterns. Nothing structural, nothing tonal.
Conflict rule
Apple wins on form. MAPEI wins on substance. If a Fiverr pattern conflicts with either, it is dropped.
Ref 01

Apple — the interaction and craft standard

Not screens to imitate. Fourteen specific behaviours, each of which will be verifiable in the prototype.

Navigation & structure

  • Push / pop stacks per tab. Each of the five tabs keeps its own navigation stack and its own scroll position. Leaving Calculator mid-flow and returning finds it exactly as it was — this is what makes §40's state preservation real rather than a patch.
  • Large title collapsing to inline on scroll, with a hairline appearing under the nav bar only once content is beneath it.
  • Parent-labelled back. ‹ Products, never a bare chevron. On a site with no signal and gloves on, the label is the orientation.
  • Grouped inset lists as the default container — the Settings pattern. Rows, hairlines inset to the text edge, section headers in secondary grey. This is what replaces cards throughout (§12).

Disclosure & input

  • One decision per screen in Calculator and System Selector; nothing else competes for attention on those screens.
  • Sheets with detents. Medium detent for the system-layer peek and the save-project prompt, expanding to large on drag. Grabber, dimmed backdrop, swipe-to-dismiss.
  • Disclosure rows for advanced settings — collapsed by default, MAGIECHEM® recommended values already applied, so the default path never sees them.
  • Segmented controls for ft² / m² and Product / Complete System — binary choices that must show both options at once.

Search

  • Spotlight behaviour, not website behaviour. Tapping search takes over the screen, results appear per keystroke, results are grouped by type with section headers, and the empty state shows recents rather than a blank field.

Craft

  • Typography as the hierarchy mechanism — weight, size and colour do the work that colour blocks and boxes do on industrial apps.
  • 44 pt minimum targets, 16 pt margins, 8 pt spacing grid. No exceptions on primary controls.
  • Motion that explains state only. Sheet rise, layer expansion, results counting into place. Nothing decorative; prefers-reduced-motion honoured.
  • Sticky bottom action bar carrying exactly one primary action, over a blurred material with a hairline above it.
  • Skeletons, not spinners; written empty states, not blank screens.

What I will not take from Apple: its screens, its icon set redrawn literally, or its consumer warmth. This is a work tool used in a mechanical room, not a lifestyle app.

Ref 02

MAPEI — content architecture and professional vocabulary

MAPEI has already solved something genuinely hard: organising a very large technical catalogue in terms a trade professional recognises on sight. That structure is worth inheriting. Its visual execution is not.

Retained

  • Product families as the catalogue's top level — Epoxy, Polyaspartic, Polyurethane, Cementitious Polyurethane, Primers, Membranes, Repair Materials, Sealants. This is how the trade already thinks; inventing a new taxonomy would cost recognition for no gain.
  • Systems as first-class objects, distinct from products. A system is a named, engineered assembly with ordered layers — not a category of products. This is the single most important structural inheritance, and it is what makes §4's philosophy expressible in the IA.
  • Dual-vocabulary browsing. Professionals arrive either by place ("mechanical room", "parking deck", "food & beverage") or by property ("chemical resistance", "ESD", "slip resistance"). Both are first-class entry paths into Systems.
  • Tools as a permanent destination. The calculator earns a bottom-nav slot rather than living inside a portal.
  • Document rigour. TDS and SDS are canonical, versioned, named as the industry names them, and never more than one tap from the product.
  • Unapologetic terminology. Mils, DFT, mix ratio by volume, pot life, recoat window, broadcast rate, solids content. No consumer translation layer.
  • Product number as the primary key. 9461 is the name; the description is the subtitle. Pros search by number.

Improved

  • Colour-coded category tiles → typographic rows. Category colour is decoration carrying no information; a row with a count carries more and weighs nothing.
  • Portal wall → open access. Search, catalogue, documents and calculator all work signed-out (§15). Authentication appears only at save.
  • PDF as the destination → data first. Mix ratio, solids, thickness, coverage and working time live on the product screen. The TDS becomes confirmation, not the source. This alone removes steps 5–9 of the workflow in §1.
  • Build-ups as static tables → an interactive cross-section. The system stack becomes a tappable technical drawing, which is the app's signature screen.
  • Separate search silos → one universal index over products, systems and documents.
Ref 03

Fiverr — four composition patterns, nothing more

  • Search-first home. The search field is the hero of Home, above any promotional or editorial content — which is the correct priority for a lookup tool.
  • Horizontal rails for lightweight discovery, used only for Recently Viewed and Recent Systems, with disciplined card proportions and a peeking next item that signals scrollability.
  • Confident section headers with a quiet "See all" on a white canvas — clean sectioning without boxes.
  • Bottom-navigation proportions — icon size, label size, and the spacing between them, which Fiverr resolves well at five items.

Explicitly refused

  • Seller cards, ratings, reviews, social proof
  • Marketplace language — "orders", "packages", "deals", "starting at"
  • Promotional banners and price emphasis
  • Any suggestion that products are being sold rather than specified

Additional references — awaiting your approval

Four requests. Each names a gap the approved three genuinely do not cover. None will be used unless you approve it individually; if you approve none, the product still works, with the consequences noted.

Flighty

Recommended
Principle
A vertical timeline of ordered, tappable segments where each segment carries dense technical values calmly, and tapping one opens a detail sheet without leaving the timeline.
Applies to
System Detail — the System Build-Up cross-section (§24), and by extension the calculator's per-layer results.
Why the three fall short
Apple ships no stacked-assembly pattern anywhere in its system apps. MAPEI renders build-ups as static tables or PDF images — precisely what we are removing. Fiverr has no technical surface at all. This is the app's signature screen and it currently has no reference.

Perplexity

Recommended
Principle
An answer with inline source attribution — every claim carries a tappable citation back to the document it came from, and the interface visibly refuses to answer beyond its sources.
Applies to
Natural-language technical search (§19).
Why the three fall short
None has an AI answer surface. §19 requires that answers cite products, systems and TDS sources and feel trustworthy — a technical recommendation without provenance is a liability in this industry. The citation pattern is the mechanism that makes the trust visible.

Google Maps — offline areas

Recommended
Principle
Explicit, user-controlled offline availability: "make this available offline", a clear per-item download state, and an honest banner when showing cached data.
Applies to
Document Center, Product Detail documents, and Project Detail — "Make this project available offline".
Why the three fall short
§34 places users in mechanical rooms, basements and warehouses. Apple's Files handles downloads but not the deliberate "take this area with me" gesture; MAPEI assumes connectivity; Fiverr is irrelevant here. Without this, the app fails exactly where it is most needed.

Soulver

Optional
Principle
Live recalculation with visible units — every dependent value updates as an input changes, and units are part of the value rather than a separate control.
Applies to
Calculator area entry and advanced settings (§26–27).
Why the three fall short
Apple's Calculator is not a parametric form; MAPEI's is a submit-and-reload web form. §40 requires that changing area, system or waste updates quantities — this reference is how that feels immediate rather than transactional.
If you approve none: the cross-section is designed from first principles, the AI surface is deferred out of the MVP, offline is reduced to a plain per-document save, and the calculator recalculates on a Calculate button rather than live.
Part 2 — Strategy, architecture and plan
A

Product strategy

The problem, stated precisely

The fifteen steps in §1 are not fifteen tasks. They are one task — specify a floor — fragmented across four systems that do not know about each other: the website, a PDF, a portal, and a calculator. The cost is not only time; it is that the professional must hold the answer in their head while moving between tools, on a site, often with gloves on.

The app's job is to collapse those four systems into one index where a product knows which systems use it, a system knows its layers and their coverages, and a calculation knows both.

Value proposition

From "I have a project" to "I know what to order" in under a minute, without opening a PDF. Everything else the app does is in service of that sentence.

Users, and what each one needs first

Flooring contractor
On site, mid-job. Needs mix ratio, pot life, recoat window and coverage in under ten seconds. Optimise for: search speed and the product screen's top block.
Estimator / PM
At a desk or in a truck. Needs area → system → kit counts, saved and shareable. Optimise for: the calculator and the material list.
Architect / engineer
Specifying. Needs the complete assembly, its thickness, its resistance data and its documents. Optimise for: System Detail and Document Center.
Distributor
On a call. Needs product lookup, compatibility and what to quote. Optimise for: search results and the material list.
MAGIECHEM® rep
In front of a customer. Needs to answer, recommend and calculate without a laptop. Optimise for: the whole app — this user touches every screen.

Design philosophy

  • Data before documents. The TDS is a fallback, not a destination.
  • Systems before products. Products are components of engineered assemblies; the IA says so structurally, not with marketing copy.
  • Answer, then elaborate. The essential values are on screen immediately; everything else is one disclosure away (§35).
  • Nothing invented. No technical value or recommendation is shown unless it traces to MAGIECHEM® source data (§19).
  • Earned identity. Brand comes from the logo, restrained red, the system names and the cross-section — not from colouring the interface (§46).
B

Information architecture

Five tabs, three of which are indexes and two of which are tools. The important structure is not the tabs — it is the cross-links between them, which is what makes the fifteen-step workflow collapse.

Connective rule
Every product links to the systems containing it; every system links to its products; both link into the calculator; the calculator links into a project; a project links back to all three. No leaf is a dead end.
Depth ceiling
Three levels from any tab root to any leaf. Anything deeper becomes a sheet.
Search placement
Modal over the current tab, returning to it on dismiss — so search never costs the user their place.
Document Center
Reached from Home search, Products and Projects rather than owning a tab. It is an index, not a destination — a sixth tab would break §5's five-item limit for a surface users arrive at by intent, not by browsing.

French-proofing (§33)

  • Every label allocated 1.4× its English width; nothing sized to fit English exactly.
  • Buttons are full-width or hug with generous padding — never fixed-width.
  • Rows support two lines of title before truncating; truncation is mid-string for product names, never for technical values.
  • Tab labels are the four longest strings in the app; they are validated in French first, and the tab set is chosen so all five fit at 10 pt.
  • Units and number formats localise together — 12,500 ft² / 1 161,3 m².
E

Functional prototype plan

Eight screens built to full behaviour, covering flows A–D end to end (§38–41). The three remaining tab roots are built because §42 forbids dead buttons — they are functional, just not where the depth goes.

  1. Home — search entry, three entry actions, Continue card, Recently Viewed rail. Recents populate from real navigation during the session.
  2. Universal Search & Results — modal takeover, live filtering per keystroke across products, systems and documents, grouped results, recents when empty.
  3. Product Detail — spec block, sections, documents, and three working actions including Calculate Quantity, which pre-fills the calculator.
  4. Document Viewer — in-app TDS with back, title, in-document search, share and save. Returns to Product Detail with scroll position intact.
  5. System Detail — the interactive cross-section. Every layer tappable to a sheet carrying that product's data, with View Product pushing to screen 3 and Calculate This System pushing to screen 7 with the system pre-selected.
  6. System Selector — three steps, real filtering logic over the system data, a recommendation with a stated reason, and both result actions live.
  7. Calculator — area with unit switching, product-or-system choice, system selection with search, waste allowance, collapsed advanced settings with real defaults.
  8. Results & Project — per-layer requirements and order quantities, Save to Project with the anonymous sign-in sheet, then Project Detail and Material List with everything preserved.

How state connects

One store above the navigation stack, so back navigation cannot lose anything. Results are derived, never stored — which is what makes §40's requirement true by construction rather than by patching.

catalog products · systems · documents (seed data, read-only) session recentProducts · recentSystems · favorites · lastCalculation calculator area · unit · target{product|system} · waste · overrides{} └─ results = derive(catalog, calculator) ← recomputed on every change projects [ { name, client, area, systemId, calcSnapshot, docs, notes } ] auth anonymous | account (gates saving only) nav { home:[…], systems:[…], calculator:[…], products:[…], projects:[…] } per-tab stacks + scroll offsets — tab switching never resets a flow

Calculation engine

Real arithmetic, not mocked numbers — so changing area, waste or system produces defensible results.

// liquid layers gallons = area_ft² × DFT_mils ÷ (1604 × solids_fraction) withWaste = gallons × (1 + waste) kits = ceil(withWaste ÷ kitSize_gal) // broadcast media pounds = area_ft² × broadcastRate_lb_per_ft² × (1 + waste) boxes = ceil(pounds ÷ boxWeight_lb) // 1604 = ft² covered by 1 gallon at 1 mil, 100% solids
Data integrity. Product values in the prototype are placeholders and will be visibly marked as such until MAGIECHEM® supplies the source TDS figures — coverage, solids, kit sizes, broadcast rates, pot life and recoat windows. Per §19 I will not publish invented technical values in a document a contractor might act on. The engine is real; the numbers it multiplies must come from you.
